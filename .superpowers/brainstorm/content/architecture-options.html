Arquitectura del sistema EcoVolt — elige un enfoque

Todos cumplen los patrones requeridos. La diferencia está en cómo se organizan las capas.

🌐 FastAPI — Endpoints REST + HTML Templates
⚙️ Services — Lógica de negocio + Patrones
🗄️ Repositories — SQLite + Estructuras de datos
📡 Sensors — Simulador / Puerto Serial

A — Arquitectura en Capas (Layered)

Capas verticales clásicas. Cada capa solo habla con la inmediata inferior. Simple, directa, fácil de entender y presentar.

Pros

  • Muy fácil de explicar
  • Estructura clara de carpetas
  • Ideal para presentación académica

Contras

  • Capas acopladas hacia abajo
  • Menos flexible para swappear DB
📡 Serial Adapter
🔮 Simulator Adapter
🏗️ DOMAIN CORE — Entities + Patterns + Data Structures
🗄️ SQLite Adapter
🌐 FastAPI Adapter

B — Hexagonal / Ports & Adapters ⭐ Recomendado

El dominio al centro, todo externo son adaptadores. Swappear simulador ↔ hardware real es trivial. Demuestra el patrón Adapter de forma auténtica.

Pros

  • Adapter pattern nativo
  • Fácil de testear (mock adapters)
  • Simul/Real: cambio de 1 línea
  • Profesional y educativo

Contras

  • Más archivos/interfaces
  • Más complejo de arrancar
📡 Sensor Producer → [QUEUE] → Event Consumer
⚠️ Alert Engine → [STACK] → Notifier
🔄 Scheduler → [CIRCULAR LIST] → Panel Monitor
🌐 FastAPI ← State Store ← Processors

C — Event-Driven con Estructuras de Datos Centrales

Las estructuras de datos (Queue, Stack, Circular List) son el núcleo de comunicación. Cada lectura de sensor es un evento que fluye por las estructuras.

Pros

  • Estructuras de datos muy visibles
  • Demuestra FIFO/LIFO claramente
  • Muy visual para presentar

Contras

  • Más complejo de depurar
  • Async/threading requerido

⭐ Recomendación: B — Hexagonal porque el requerimiento de soporte dual (simulador + hardware real) es exactamente el caso de uso del patrón Adapter. El dominio no sabe si los datos vienen de un Arduino o de un generador Python — solo habla con la interfaz.
